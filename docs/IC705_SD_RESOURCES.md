# 日版 IC-705：开机图片与菜单字库的加载对照

2026-11-13，2026-11-14 补测。样本为 Icom 日版 J132 与 J140，使用[已验证的主程序镜像](MAIN_CPU_DECODE.md)在 Windows 进行静态分析和原厂 ARM 例程回放。两版都能从文件任务进入开机图片导入；J140 已从完整资源函数入口连续运行到两张字库登记，并用同一回放实例绘出原厂「表示言語」。目前已识别的菜单字体初始化使用固定 Flash 记录。开机图片入口不能给菜单载入中文文案或字体。

## 原厂开机图片：文件加载的对照

[Icom 日版取扱説明書](https://www.icom.co.jp/support/manual/4873/) A7577D-1J-8，印刷页 6-1、13-19、13-24、14-10。用户在 SD 的 `OpeningPicture` 文件夹放入 480×272、24 位 BMP，再从设置导入；导入后移除 SD 仍可显示。手册也分别描述了设置文件、CSV 和显示／系统语言。以下反汇编中的 `C:\IC-705\Opening\opening.bmp` 是固件使用的内部路径，不是手册里的用户目录。

| 数据流 | 日版 1.32 | 日版 1.40 |
| --- | --- | --- |
| 内部路径常量 → 写入文件命令 `0x37`，模式 0 | `0x200F5BF8` → `0x20067D78` | `0x200F9188` → `0x20068F90` |
| 文件状态 `0x203802BC+0x60` → 分支表 → 图片导入 | `0x20070A74` → `0x20070B60` → `0x20068230` | `0x20071C8C` → `0x20071D78` → `0x20069448` |
| 读取 54 字节头部并送入 BMP 校验 | `0x20068334` → `0x20068370` 调用 `0x2012DED0` | `0x2006954C` → `0x20069588` 调用 `0x20131538` |
| 分块读像素、内联 RGB565 转换 | `0x20068404`、`0x20068448` | `0x2006961C`、`0x20069660` |
| 另一图片文件例程中调用独立 RGB565 转换 | `0x2006EF30` → `0x2012E164` | `0x20070148` → `0x201317CC` |

在 Unicorn 内，原厂封装例程把内部路径写进 RAM，请求唤醒文件任务；在唤醒边界暂停，再执行原厂分发表，确实到达 `0x37` 导入例程。分别调用同一个原厂 BMP 校验函数：合成的合法头返回 0，错签名和宽 479 都返回 1。用独立 RGB565 转换例程处理同一张合成图，两版各输出 261,120 字节；整个缓冲逐字节匹配预期的红、绿、蓝、白重复序列，SHA-256 同为 `7429a36d1ba9ed80be796942d3744e9781e16ab089edcad1fb0a4834fb474ba8`。分块导入和持久化代码只做静态检查；未模拟 FAT、Flash 写入或冷启动，也没有读写真机 SD。

这给 SSTV 提供一个独立的原厂图片格式和像素输出对照。SSTV 收图的逐行绘制、图像浏览和 microSD 保存还需要分别定位及验证。

## 菜单字体：固定记录的对照

用两组不同的合成长度填入模拟 Flash `0x18C00000` 与 `0x18FA2588`。分别执行 J132 `0x20101364`、J140 `0x20104984` 开始的十条原厂指令：两版从对应 Flash 记录复制长度，并写入同样的两个字体指针 `0x18C00004` 和 `0x18FA258C`。长度故意用合成值，目的是验证来源；真实字库大小、从显示语言到绘制的证据见[字体报告](IC705_LANGUAGE_FONT.md#字体指针的来源)。

这条字体路径没有经过文件任务。已验证的路径和手册均没有给出把外部词表或 TTF 安装为菜单资源的方式。仍不能排除其他区段、间接调用或厂商未公开的接口；在取得这种入口的证据前，六页汉化继续作为 PC 对照，不扩翻全部菜单。

### J140：从字库发现到首条测试菜单绘制

在两个全新的 Unicorn 实例里，先让 J140 原厂 ARM 自己填写字体表，再初始化 UI 字库并执行「表示言語」原厂菜单行。实验没有改主程序指令或字体表。两次唯一不同的初始资源是模拟 Flash 的大字体记录。

| 对照 | 原厂代码得到的结果 |
| --- | --- |
| 两份原厂字体 | 原厂资源段 `0x20104984` 将长度和指针写入 `0x203808A0–0x203808AF`。UI 初始化入口 `0x20141DEC` 进入 `0x20145244`，调用内置 FreeType 五次，顺序是大、小、小、小、大。「表示言語」正常提交绘制，大字体「表」字形编号 3136。 |
| 大字体位置放 18,772 字节的开源 Noto 子集；小字体不变 | 五次初始化顺序不变，两次大字库调用都收到新长度，三次小字库调用仍收到原地址及 25,636 字节。原厂菜单仍送出「表示言語」，确认换字体不换文案。 |
| 同一菜单绘制入口，受控传入 Unicode「表设简显」 | 原厂大字体只有「表」，整条测试串没有绘制提交。开源子集四字均有轮廓，原厂绘制函数提交一条四字的 OpenVG 调用，软件画布测得 650 个非透明像素。 |

模拟器提供 Flash 数据、栈、分配器和 OpenVG 后端。两组实验均从下文的原厂 `0x20104948` 分支开始写表，再调用原厂 UI 初始化和菜单绘制。测试串在字符转换后送入绘制器。**固定 Flash 记录到显示的路径接受替代字库；整机冷启动、外部资源入口和原厂中文文案来源仍未证明。**

### J140：资源函数入口与标签分支

初次实验将前后两段分开重放，保留以下基准。第一段从原厂函数入口 `0x2010490C` 执行，使用两组不同的时钟寄存器初值；第二段从分支 `0x20104948` 执行，使用合成调用栈、状态标志和 Flash 标签。下方追加实验已把两段接通。

| 对照 | 实际观测 |
| --- | --- |
| 无外设模型 | 重现旧停点：`0x20367B04` 读 `0xFCFE042C`。 |
| 仅模拟已确认的时钟门控、定时器命令和 DMA 控制写入 | `STBCR6`（`0xFCFE042C`）置位 bit 0；`STBCR5`（`0xFCFE0428`）清 bit 0；其余位保持。原厂向 OSTM1 的 `TT`、`CTL` 分别写 `1`、`2`，再分别向两组 DMA `DCTRL`（`0xE8200300`、`0xE8200700`）写入 `1`。两种初值随后都在 `0x20367B04` 读取 `STBCR3`（`0xFCFE0420`，MTU2 时钟门控）时暂停；字体表还未写入。 |
| 后段：调用方标志为 0，合成标签匹配或不匹配 | 原厂将 `0x18BF0000` 的 16 字节与内置标签比较（Thumb `0x202C9068`）；匹配写 `0`，不匹配写 `1` 到 `0x2038089D`。两者均走到 `0x201049AC`，用相同的原厂记录写入相同的字体地址和长度。 |
| 后段：调用方标志为 1，不映射标签或字库 | 原厂走 `0x201049CC` 返回，字体表保持零。调用方循环见下节的独立对照。 |

寄存器身份来自 [Linux R7S72100 设备树](https://code.googlesource.com/linux/torvalds/linux/+/3a2976df778a9af95e91f7ff88008b4517ddc658/arch/arm/boot/dts/renesas/r7s72100.dtsi)、[RZ DMA 驱动](https://code.googlesource.com/linux/torvalds/linux/+/4bf54e47525dcacd4c6cdd97fb5902592414dd7a/drivers/dma/sh/rz-dmac.c)、[Renesas OSTM 驱动](https://github.com/torvalds/linux/blob/master/drivers/clocksource/renesas-ostm.c)及 [Renesas 硬件手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware)（R01UH0403EJ0700，第 9、11、55 章）。模型只记录上述访问，没有模拟计时、DMA 传输或中断。标签地址紧跟现有模拟图形切片；对照使用固件内置 `SX4075 V0.10-000` 和故意不同的 `SX4075 V1.00-000`，未假设真机在该地址存放哪一种。比较结果在其他例程中的用途未知。

后续的[菜单资源对照](IC705_ZH_RESOURCE_ORIGIN.md)确认 `0xA7` 的日英标签指针同时服务列表行和选择器标题；早期复制、清零和原厂 ICF 解析不改这两条菜单记录及选项表。

### J140：从函数入口连续写表，并用写出的字库绘制

沿 [IC-7300 的外设对照](IC705_CROSS_MODEL_REUSE.md)补齐有限的寄存器模型。Windows/Unicorn 只接受观测到的 CPG、OSTM、DMAC、MTU2 和 GICD 地址与访问宽度；未初始化的寄存器读取报错。原厂代码启用 MTU2 的 3、4、0 通道，并写 GICD 寄存器使能中断 154、159。没有注入中断或推进定时器；移除 `0xFCFF0203` 后，原厂运行在同一位置失败，字体表仍是零。REA 核对了[原厂镜像及对应字节区间](REA_ANALYSIS.md#字库入口连续回放)。

| 从原厂 `0x2010490C` 开始执行 | 结果 |
| --- | --- |
| 时钟寄存器初值 `00` / `FF`，标签匹配 | 各完成 60 次外设访问，均到达 `0x201049AC`。原厂四条写指令填入大字库 `0x18C00004`、3,810,692 字节；小字库 `0x18FA258C`、25,636 字节。 |
| 时钟初值 `FF`，标签故意不匹配 | 比较状态位变为 1；两张字库的地址和长度仍完全相同。 |
| 时钟初值 `FF`，调用方标志为 1，不映射字体 Flash | 原厂从早退分支返回，四个字段均未写入。 |
| 把初值 `00` 的同一来宾实例交给原厂 UI 字体初始化和行绘制 | 五次 FreeType 调用读到刚写的原厂地址和长度；原厂「表示言語」一行的 PNG 与旧基准逐像素相同。 |

执行从资源函数入口到字库表未跳段、未改来宾指令；随后是独立调用原厂字体初始化和绘制例程。Flash 比较标签仍是模拟输入，未确认真机该地址的内容。整机还未从 CPU 复位跑进该函数，原生外部字库和中文选项仍未验证。

### J140：上一级任务的首次调用与重入

从原厂任务 `0x20098334` 开始，以来宾 ARM System 模式、独立的 SVC 栈和模拟 Flash 标签起步。任务先执行 `SVC 0`；回放只设置异常入口的寄存器状态并转入向量，随后执行原厂向量 `0x20005008` 和原厂处理程序。仅为 [GICC_PMR](https://arm-software.github.io/CMSIS_5/5.7.0/Core_A/html/structGICInterface__Type.html) 提供初值 `0xF0` 和读回，观察到原厂恢复 `0xF0`。REA MCP 已核对任务入口所在的 256 字节区间（文件偏移 `0x93334`，证据 `ev_5c74a2a81b366f576bcb594858ff85ca42b36f02b09168e7b3f3f4692cdfab4a`）；调用、标志和写入来自 ARM 回放。

| 试验 | 实际结果 |
| --- | --- |
| 执行原厂板级初始化，不替换返回 | 原厂任务把事先置为 `0xA5` 的标志清为 0，调用资源函数并正常返回。两张字库均已写好；下一段板级初始化 `0x2007BBA8` 在 `0x2011D514` 读取 `0xFCFE300C`（16 位）时停下。 |
| 仅让板级初始化调用立即返回，作为循环对照 | 原厂任务自己把标志写成 1，自然回到循环头再次调用资源函数。两次共做 120 次资源外设访问；第一次写表四次，第二次写表零次，已有表不变。 |

`0xFCFE300C` 位于 [IC-7300 模型定义的 GPIO 寄存器区](https://github.com/jeskko/ic7300-homebrew/blob/84fb65b457f00bddcf5fb3d044e9f29dad3be48b/qemu-machine/src/gpio.c#L38-L57)。后续复用寄存器布局继续执行板级初始化，见下节。

### J140：从 GPIO 到 ADC 和串口

仍从原厂任务 `0x20098334` 连续执行；两张字库正常登记，板级函数未被替代。GPIO 配置与输入读回分开处理。时钟和 GPIO、RIIC（I²C）、OSTM 地址参考 [IC-7300 外设模型](IC705_CROSS_MODEL_REUSE.md)及 [Renesas 提交的 R7S72100 设备树](https://github.com/torvalds/linux/blob/master/arch/arm/boot/dts/renesas/r7s72100.dtsi)。本轮只提供可复现的零输入、未从待机唤醒状态、寄存器读回与按轮询推进的虚拟计数；不是实机引脚快照、总线应答或校准后的时间。

- **识别了板级初始化对原厂引导代码的依赖。** 板级调用 `0x2007BD6C → 0x2000498C` 在原厂搬运至 SRAM 的代码里；缺少这 2,492 字节时，空白 RAM 导致探查误跑回复位入口。按[引导复制范围](MAIN_CPU_DECODE.md#从启动代码验证装载地址)映射原厂 DAT 的 `0x4000:0x49BC` 后，原厂 getter 在 `0x20004990` 读到单字节状态 `0x20004F20` 并正常返回。状态字节没有填入实机值；在本次空白 SRAM 工况下为 0。
- **无 ADC 模型：** GPIO、I²C 寄存器配置和定时等待均已越过。停在 `0x201184E4` 对片上 ADC 状态 `0xE8005860` 的 16 位读取。REA 确认 GPIO 配置和板级入口所在主程序窗口（证据 `ev_026b1eb86967de5a1d8e338dd96d8b19dd8ac12cedcdb649751acb9394011adc`、`ev_b37e5cd9f0d525f70bfbfb9a239fb299472ebf03df02efe62d12d5705976945e`）。
- **两组 ADC 对照：** 显式初始化「转换已完成」状态，分别返回 10 位测试值 384、640。两组均执行原厂 `0x201184FC` 读取 `0xE800580E` 的采样数据，随后清状态、继续走到 `0x20120DFC` 读取 `0xE8008820`。设备树确认该块为 SCIF3，[IC-7300 模型的寄存器表](https://github.com/jeskko/ic7300-homebrew/blob/84fb65b457f00bddcf5fb3d044e9f29dad3be48b/qemu-machine/src/scif.c#L302-L312)确认偏移 `0x20` 是串口引脚寄存器 SPTR。两组条件都只写表一次，字库表未被重写或清空。

ADC 的原厂转换完成事件仍待验证；本次继续追串口等待，见下节。

### J140：SCIF3 子控连线与两级等待

核对维修图 MAIN UNIT 6/8、7/8（本地 PDF 第 175、176 页）：主控的 `P5_2/P5_3/P5_4` 分别接 `SCSCK/SCTXD/SCRXD`，`P7_9` 接 `SCACK`；子控 IC901 是 STM32L051R8H6，图上可交叉确认其 `SCSCK/SCRXD` 两条线。[Renesas 引脚表](https://www.renesas.com/en/document/sch/renesas-starter-kit-rza1h-cpu-board-schematics)将对应三个 P5 引脚列为 SCIF3 复用功能，[设备树](https://github.com/torvalds/linux/blob/master/arch/arm/boot/dts/renesas/r7s72100.dtsi)将 SCIF3 映射在 `0xE8008800`。J140 反汇编中的引脚配置及 `0x201208BC` 对 P7 第 9 位的轮询与图纸一致。这个对端是 705 的子控；未套用 IC-7300 的面板协议。REA 复核了主程序窗口 `0x11BDE0` 和 `0x11B87C`（`ev_403a6f61b4d882d9fd0dcfb4fa79703e6e1730b218ea697bc72bfd7d4c0fc068`、`ev_f800eb1f908a67725c7d7444b02a79cdcfe7eb2d2b5bac41e0652876cfe75e1b`）。

两个对照从同一个原厂任务起步，使用相同 ADC 样本 384、低电平 `SCACK` 和空接收 FIFO。原厂 `0x20120DE0` 配置 SPTR、SCR、FCR、SMR、BRR，返回到 `0x20121CF4`。在此后的两个工况里均未读写串口数据 FIFO，也未执行 DMA 传输。

| 对照 | 原厂执行结果 |
| --- | --- |
| 不提供计时器匹配 | 原厂在 `0x201208BC` 轮询 `SCACK`，并检查 `0xFCFF0305` 的计时器状态位。到观测上限时忙状态为 1。 |
| 仅提供计时器匹配，不提供子控信号或字节 | 原厂沿 `0x2012096C` 的超时分支继续，在 `0x20120B80` 向 `0xFCFF0228` 写入下一次比较值 1600、使能 GIC 中断 161，然后在 `0x20121D54` 等待，忙状态变为 2。测试按轮询提供第一次比较标志；1600 是寄存器值，未换算为实机延时。 |

### J140：原厂中断回放越过串口等待

从上述超时分支连续执行。回放在来宾自行注册并使能对应中断后，提供计时事件或接收 FIFO，并按 [Arm IRQ 及 GIC 接口](https://support.arm.com/documentation/ihi0048/b/Interrupt-Handling-and-Prioritization/General-handling-of-interrupts?lang=en)设置异常入口状态。为替代之前未执行的中断控制器初始化，给来宾中断表的范围字段设定测试上界 236；表项仍由原厂注册代码写入。来宾实际执行原厂 IRQ 向量 `0x20005018`、分发器 `0x200051C8`、各处理例程、GIC 应答和 `RFE` 返回；脚本不写忙标志、不替换处理函数，也不跳过来宾分支。

| 对照 | 原厂执行结果 |
| --- | --- |
| 只给第二次计时中断 161 | 处理函数 `0x20120658` 清除计时状态、禁用这一轮计时 IRQ，把 SCIF3 `SCR` 写成 `0x50`，开启接收和接收中断。返回后忙标志仍为 2，继续在 `0x20121D54` 等待。 |
| 再给接收中断 235，FIFO 为 `FC 00 39 00` | 原厂例程 `0x20120BC8` 从 `0xE8008814` 读完四字节并重新开启接收。忙标志保持 2。 |
| 同样给接收中断 235，最后一字节改为 `FE` | 原厂在 `0x20120CAC` 走拷贝分支，将测试值 `39` 存入 `0x20499553`；在 `0x20120DCC` 清除忙标志。中断正常返回后，启动代码退出等待，首次执行到 `0x20121D60`。 |

主控接受这组测试输入；它来自原厂解析分支，未测定真机子控实际回复的时刻、长度或内容。REA MCP 对原厂镜像字节取证：IRQ 向量和分发（`ev_a4fc0c4be838b2e224c39cc1edc4d0a524ddbd752afa6f7ea2f01d5220aea1a4`）、计时处理（`ev_3a4f776c826815a40359381f19898dba7677e953884d3d7dd7e35e6fb9326d35`）、接收处理（`ev_6da01ed2f2ae21b3da4076c1207591da02ca71a3aa0ad4886c3aa822f82da80d`）。

### J140：原厂串口返回与板级电源分支

**串口返回通过；板级初始化返回未通过。** 在两组 PC 回放中，原厂串口例程均执行 `0x20121DF4` 的函数尾并回到板级调用方 `0x2007BE78`。这是 `0x2007BBA8` 里的直接调用，之前列出的 `0x2011D754` 是另一条调用路径。没有替代串口函数的返回，也没有改写板级返回地址或板级状态标志。

回放使用原厂搬运例程，将镜像 `0x20367B78` 的 `0x1F44` 字节写入 `0x20380000`，恢复之前直接从任务入口起跑时遗漏的任务描述和中断表。随后进入原厂 RTX 启动代码。在低电平对照中，原厂任务经 OSTM IRQ 134 和软件中断 SGI 0 挂起、恢复；应用侧 IRQ 159 经原厂向量和中断处理函数推进计数 `0x203808D0` 至 35。实验在轮询边界提供中断事件，不能换算为实机时间。

| 唯一改动的回放输入 | 执行观察 | 验收 |
| --- | --- | --- |
| `P3.9=0` | 串口返回后，执行紧邻板级函数尾的 `0x2007C318 BL 0x2007B858`。又处理一帧测试输入后，经 `0x200788E0` 进入 `0x2007814C`；原厂后续指令向看门狗寄存器写值，本次在写入前停止。 | 未执行板级函数尾 `0x2007C31C`，也未回到 `0x20098394`；板级标志仍为 0。 |
| `P3.9=1` | 串口返回后，直接经 `0x200788E0` 到达 `0x20078520` 的原厂 `WFI` 待机循环，未进入 `0x2007B858`。 | 未观察到板级返回；板级标志仍为 0。 |

维修图 MAIN UNIT (6/8) 给出 `P3_9=W20 VBUS`；表中的高低电平是仿真输入，不等同于真机 USB 插拔对照。串口帧 `FC0039FE`、ADC 样本 384 与补充外设寄存器值均为测试输入。置信度：对上述 PC 路径与返回点为高；两条分支在真实上电中的适用条件尚未验证。

分岔位置已缩到 `0x2007C218` 的原厂 VBUS 查询。跟踪到两组都以运行模式 2 进入 `0x2007C1AC`；低电平把模式改成 3，再调用 `0x2007B858(3)`，高电平保留 2 并先走 `0x2007C310`。将低电平组的固定 ADC 样本从 384 分别改成 640、760、900，三个试跑均保持 2→3 和同一复位入口；固定样本不是按通道或时序的供电模型。下一项追模式来源和允许继续启动的条件：低电平分支在 `0x2007C204` 还检查 `0x2000E078` 的结果，另一条路径在 `0x2007C228` 读取 `0x2000D630` 的结果。需要从产生这些状态的外设输入着手，以正常上电与缺事件为对照；通过条件仍是原厂执行 `0x2007C31C` 并返回 `0x20098394`，待机或复位不算。

2026-11-14 续测：REA 对 `0x2007C204` 起 256 字节的原厂文件窗口取证（`ev_fe9b2cbe2297cd523551c0aca7268152e982177e9a26286b0b5300dab2419b38`）。在一次性仿真对照中，以 0 为原始状态，分别给 `0xFCFF1808` 初始值 `0x0008`、`0x0010`、`0x0400`、`0x2000`，并回读原厂清除后的值；只有 `0x0400` 改变低电平路径（2→2，停在原厂待机而非复位入口）。它没有使板级初始化返回，也没有确认实际电源键对应哪一位或触发时序。这里仅改变虚拟外设输入；这些探针未合入默认回放。[电脑预览的重启保存](IC705_ZH_THIRD_LANGUAGE.md)单独验收。

## J140 原厂电源键唤醒与首个 I²C 请求

## J140 首个 I²C 请求完成与下一次读取

复用按住电源键的启动回放。对照 [R7S72100 RIIC0 中断表](https://github.com/torvalds/linux/blob/master/arch/arm/boot/dts/renesas/r7s72100.dtsi)和原厂注册表，分别提供 START、TX ready、TX end 和 STOP 状态。原厂中断入口执行发送、清状态和返回；宿主没有写原厂请求状态、替换驱动或注入 EEPROM 内容。

| PC 对照 | 原厂结果 |
| --- | --- |
| 只到发送结束，不提供 STOP 通知 | 原厂依次向发送寄存器写 `A6 FD 80 80 00`，请求 STOP，事务状态保持 6，未返回调用者。 |
| 同样发送，另提供 STOP 通知 | 原厂 STOP 处理将事务状态清零，驱动正常返回 `0x2005E5C0`。继续运行原厂代码到 `0x2005E3CC`，观察到长度 16 的 EEPROM 读取请求，地址字段 `0x3FE40`。 |

首字节 `A6` 的七位地址为 `0x53`，方向为写；按 [GT24C1024 数据手册](https://www.giantec-semi.com/uploads/pdf/241105/ct/GT24C1024_DS.pdf)，`A6 FD 80 80 00` 对应地址脚 A2=0、A1=1 的器件，内部偏移 `0x1FD80`，写入 `80 00`。这是基于原厂发出的字节和器件协议的解释；尚未在实机总线上核对，也未将这些字节写入真实设备。后续读取改由 GPIO 逐位驱动：反汇编显示读函数用端口读数逐位拼字节，而非等待同一组 RIIC 中断。下一步在模拟器中补这段读取的数据与应答，用两组不同已知内容验证原厂确实按位读回，再追设置加载或首页。不能把现有固定低电平读回造成的全零当作真机数据。

双击 `Verify-IC705-Startup-I2C.cmd` 可复跑，两组证据写入 `.analysis/ic705-emulator/j140-riic0/riic0.json`。REA `inspect_byte_entropy` 核对原厂中断、驱动与注册代码所在文件范围（偏移 `0x568D8`、长度 `0x1040`，证据 `ev_3009fc1b8547a7dfce79f108c19a0d8facd43cb9edacf91054feebfa02728fd4`）。GNU 反汇编与 ARM 回放分别复核指令和上述执行轨迹。对受控回放结果的置信度高；原厂板级启动返回和首页仍未观察到。

## J140：启动读完 EEPROM 扫描并等待板级队列

在同一开机实例继续。原厂配置两路串行控制器（`0xE800C800` 与 `0xE800E000`，各自命令寄存器写 `0xE78C`、`0xE70C`），再运行 EEPROM 扫描。这两处仅模拟所观测的寄存器读写。资料：[Renesas RZ/A1H 硬件手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware)。

- 扫描先请求逻辑地址 `0x550F` 的 18 字节，实际发送 `A0 55 0F A1`，原厂逐位读入 144 位并完整复制一份非重复合成样本。后续读取均供给 `FF`，共 **11,170 次、79,982 字节**，逐次核对位数和缓冲区。地址字段与长度的顺序记录按 `<IB` 打包后计算 SHA-256。这个数量包含重复读，不能当作 EEPROM 容量或备份范围。

- 主任务仍持有 CPU；监听原厂界面入口 `0x2013D564`，两次均无执行。合成 EEPROM 试验只能证明原厂执行过这段扫描及到达下一等待点，不能证明真机使用同样的记录、已经绘制首页或可以恢复。

## J140 开机配置 CW 使用的收音缓冲

从六个板级版本查询之后继续运行原厂指令。原厂先配置 SCUX、三路串行音频接口与四路音频 DMA，然后读取音频帧同步线 P2.9。维修图与寄存器定义的对应关系见[音频硬件记录](IC705_RX_AUDIO.md#信号与地址)；SCUX 基址亦与 [Renesas 寄存器定义](https://github.com/ARMmbed/mbed-os/blob/master/targets/TARGET_RENESAS/TARGET_RZ_A1XX/TARGET_RZ_A1H/device/inc/iodefines/scux_iodefine.h)吻合。

- 保持 P2.9 为低，原厂重复读取，四路 DMA 均只写过复位命令，尚未启用。继续提供低/高交替的合成输入，原厂通过十个同步检查点，启用四路 DMA 并从音频初始化返回到 `0x2007B43C`。

## J140 开机清屏写入 LCD 缓冲区

另一方面，原厂独立向 OpenVG FIFO 连续提交了 21 次 RGB565 填充命令。仿真按原厂命令实现这批填充。前两次各写完 480×272 像素，实际把预填为 `0xBEEF` 的两块缓冲区改为黑色；地址分别为 `0x208AE000` 和 `0x208EDC00`。随后原厂用 960 字节行跨度把第一个缓冲区写进 LCD 的 GR2 读地址，并打开该层的读取。回放核对了整个 LCD 缓冲区的字节和哈希；这是原厂开机产生的黑底内容，尚未确认屏幕扫描、开机标志或首页。填充命令的格式参考同芯片 [OpenVG 模型](https://raw.githubusercontent.com/jeskko/ic7300-homebrew/84fb65b457f00bddcf5fb3d044e9f29dad3be48b/qemu-machine/src/openvg.c)，LCD 读地址和行跨度由原厂寄存器轨迹独立核对。

### J140 首帧之后的收音与显示等待

### J140 当前格式的正常启动对照

用 `SX4075 V4.51-J00` 作合成设置标记。旧格式函数 `0x20068E30` 只比对表 `0x202E2050` 的前五项，均不匹配；返回 `0` 在这里表示**不请求旧格式转换**。原厂随后走 `0x2007B540`，从 EEPROM 再读同一标记并与程序内置字符串比较。本轮录得 12 笔后续 GPIO I²C 读取，五个检查返回点均为 0。关键合成数据如下，按 GPIO 读取入口看到的 18 位地址记录；I²C 从地址和芯片内偏移另见报告。

| 读取入口地址 | 测试输入 |
| --- | --- |
| `0x3FE40` | `SX4075 V4.51-J00` |
| `0x1AAE1` | `06` |
| `0x1EA30` | `IcomCloneFormat3`（数据取自原厂常量） |
| `0x3FD83` 到 `0x3FD86` | 四个待初始化标记清零 |

只填前三项、把待初始化标记保留为 `FF` 时，原厂在第九笔读取后试图写 16 字节到逻辑地址 `0x2EA3B`。这与旧格式转换尝试写 `0x3FCC0` 是不同路径；两项均停在写入入口。将四个标记置零后，原厂继续完成 PWM 通道 1 设置（[Renesas RZ/A1H 手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware)，Rev. 7.00 §52.3）。模型只接受观察到的五个寄存器及访问宽度，不模拟输出波形；未把该通道认作设备上的特定功能。

随后原厂在 `0x2006C2B4` 从 `0x18852000` 读取四个零字节。它们来自升级文件 A 组解码后的 `0x262000`，按已有图形资源基址 `0x185F0000` 只读映射。设置初始化执行 `0x2007B704` 返回外层 `0x2007B8B8`；外层又读 `0x3FD87` 的 10 字节和 `0x3FD91` 的 11 字节（均为合成 `FF`），未进入设置写例程。REA 核对两个主程序文件窗口：`ev_102c2f52dc13cbf1836ecf4a57dae51aba7b98a77baa1f166d56dc89bcf911c3`、`ev_16f101e8b3cea0a1bd7c10b1d78d24d93c15ce14436a8beb177727496f9b9103`。

原厂随后自行调度界面任务 `0x20499794`，进入 `0x2013D564`，收到请求 `2`。任务等到模拟的图形模块退出待机，配置 480×272 的显示控制器，使能 78 号显示行中断，并提交首条 OpenVG 命令。仿真提供 GPU 完成中断后，原厂继续完成字体与画布初始化。

当前格式下，请求 `2` 实际提交的是**黑色开机首帧**。原厂清空两块模拟 LCD 缓冲，未调用旧格式用的 `0x2013D4A4` 场景分派，没有绘制转换文字。合成命令完成后，LCD 读地址从 `0x208AE000` 切到 `0x208EDC00`，两块缓冲的像素均为黑色。单独的显示行事件没有清除请求；模拟垂直同步完成后，原厂自行把请求从 `2` 清零。这说明两种格式虽然提交了相同的请求编号，实际画面并不相同。

随后一个模拟计时器中断让原厂启动任务 `0x20499760` 继续执行 `0x2007A720`。原厂配置并启动 MTU2 通道 1（[Renesas 手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware) Rev. 7.00 §10.2、§10.3.2），执行 DMA 通道 2 的三条寄存器写入（`0x2008D06C/74/7C`），并经原厂 RIIC0 驱动完成六笔 EEPROM 请求。该 DMA 通道不是已验证的收音通道。

同一启动实例从模拟 GPIO EEPROM 自行取出合成 VFO 值 **7.030 MHz**，在原厂 `0x20062764` 查找例程核对输入，其后经 GPIO 实际读完 `0x37C8F` 的 12 字节及 `0x3FD82` 的一个字节（均为合成 `FF`）。回放只通过模拟总线应答提供测试数据，没有写入来宾 VFO 状态。对应 REA 窗口 `ev_796c79d2f594f11feeeadff22a0ee862e0020bfa87f2dc77c7dd82233e138915` 和 `ev_a85ebb316cfd39f004af9dc08e8a58d16b60cbe33a40ae6b0934a5b8ed505359`。

对官方包未携带的可选 Flash 记录，只在原厂读取 `0x18FFFFF0` 时返回擦除值 `FF`。原厂比较不相等，随后提交场景 `04`，即开机进度动画。静态对照 `0x20090E1C` 写入场景号；实跑确认 **IRQ 159** 经原厂三级分频后，每 40 次比较推进 16 位计时变量 `0x2040204A` 一刻度（`0x2010537C–0x20105384`）。IRQ 154 唤醒任务，单独运行不会推进这个计数。此为可选记录缺失时的对照；没有断定真机记录也是 `FF`。合成设置和只读 Flash 切片均不是实机备份。

原厂用 FIFO 指令清空一块 **34×33** 的 A8（每像素一个透明度字节）缓冲。回放逐行确认目标像素归零而填充区外的行尾不变。和原厂第一次黑色 LCD 帧逐字节对照，屏幕缓冲此时未变。模拟的绘图完成通知由原厂中断处理，界面任务继续提交边界 `[150, 175, 184, 208]` 的矩形及后续绘图。REA 核对原厂写命令与参数窗口 `ev_607560463219d0d4e9057966390d1086d1104b84deb675c7dbfaa1fe97339d03`；A8 两字长目标描述和掩模混合参照同芯片的 [IC-7300 模型](https://raw.githubusercontent.com/jeskko/ic7300-homebrew/84fb65b457f00bddcf5fb3d044e9f29dad3be48b/qemu-machine/src/openvg.c)，由日版 1.40 的 FIFO 实跑验证用到了相应格式。

原厂进一步把 126×21 的开机标识遮罩从只读 Flash `0x18BDEFC0` 复制到绘图 RAM `0x208697A0`，源和目标逐字节一致（SHA-256 `3e88d44e5466f1dd80abc008b6bb63d53f97e3e0ef8c097a69d17888e28be3be`）。`boot-progress-mask.png` 来自该复制。在 100% 帧中遇到的 A8 操作 `0x61000092 / 0x80121051` 现按 [OpenVG 1.1](https://registry.khronos.org/OpenVG/specs/openvg-1.1.pdf) §10.1、§10.8 使用白色和图像自身的透明度，与另一条带画笔颜色的遮罩分开。模型单测核对全白、半透明白覆盖底色、边界外不变；未宣称像素和真机抗锯齿逐位相同。

同一个原厂程序实例通过计时器走完了场景 04 的 **21 次换屏**：Icom 标志淡入、版本及完整画面、保持、最后淡出到黑屏。中间满亮帧为 7,865 个非黑像素（`boot-full-lcd.png`），最终帧和第一帧逐字节相同。逐帧对照普通行中断不清除待换帧，原厂垂直同步才确认完成；模拟 DMA 只报告运行，无伪造的已完成音频。

场景结束前，原厂读取静止旋钮计时器、启用 SDHI 时钟并读回（到 `0x2012635C`），再经原厂引脚配置完成 **SDHI0 空槽场景的主控初始化**，返回调用方 `0x2007ADA8`。按 [Renesas RZ/A1H 手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware) Rev. 7.00 §50.2、§50.3.2，模拟无卡和无插拔边沿，逐一核对 18 笔 16 位初始化事务的指令位置、方向、宽度和值。首笔在 `0x202CADC0` 将 `0x031D` 写入 `SD_INFO1_MASK`；第 18 笔在 `0x202CDF48` 将 `SD_OPTION` 从 `0xBE` 改到 `0xB8`。随后在主循环第 19 笔读取中见 `SD_INFO1` 第 5 位为零，经 `0x202CA1F0` 走原厂未插卡分支。过程中没有 SD 命令、扇区访问、SD 中断或 EEPROM 写入；未推断插卡后的行为。REA 核对初始化、事件设置和外围初始化返回窗口：`ev_6e2662f3f354d4ae86398c8164991508f7a6c1aaaec22c7c25c3bf680aa48fcd`、`ev_702688ccf8e86f07cbbbf2c2af467ac205e25363f9961dcf1aee34dece1ce002`、`ev_6d49a94e40091a122e4c763025b684e91bd64bc98dd4e6d87c479505b5e78901`。

第 20 次换屏之后，原厂又请求一张全黑的开机帧，首次首页更新调用（`0x2007AE04`）因此在 `0x2009657C` 返回。原厂随后经 `0x2007B970` 进入正常主循环 `0x200D4E1C`。同一实例确认第 21 次换屏后，原厂界面任务清空待处理请求；CPU 在 `0x201254B0` 等待后续事件。此时**尚无原厂首页**；[冷启动到 CW 的接合点](IC705_BOOT_CW_JOIN.md)另有验收表。

继续单独给同一实例 35 次计时器中断，原厂主任务每次都醒来；但 `0x2011E114` 看到板级串行队列和 GPIO DMA 的待完成标志（`0x20380B58`、`0x20380B5C`），返回等待，未到下一次首页更新。这个对照见 `.analysis/ic705-emulator/agent-sdhi-main-timers-1114.log`。

随后在第 21 次换屏后暂停应用计时，以 IRQ 162／280 和四个合成零字节让原厂处理五个待完成的板级串行传输。原厂自行把队列读写指针推进到 46、清除忙标志。恢复一次应用计时后，原先未提供有效时钟的对照在 `0x200E4380` 要求向逻辑 EEPROM 地址 `0x3FB5C` 写零，在写函数入口 `0x2005E554` 已拦截（`.analysis/ic705-emulator/agent-sdhi-board-write-1115.log`）。

加入 RTC 外设后，同一实例用原厂 RIIC1 中断执行以下四笔交易。Icom 维修图 MAIN UNIT 6/8 的 IC751 标注 **RX8130CE**；[Epson 原厂手册](https://download.epsondevice.com/td/pdf/app/RX8130CE_en.pdf)第 13 节对应 7 位从地址 `0x32` 和下表寄存器。读序列在写寄存器索引后依次发重复 START、读地址 `65`、读数据并 STOP；数据经原厂中断处理，不直接写日期、队列或任务状态。

| 事务 | 原厂实际发送字节 | 模拟返回／写入 |
| --- | --- | --- |
| 读状态 `0x1D` | `64 1D 65` | `00`（无无效时间标志） |

保持原先的擦除值样本时，主循环执行原厂 `0x200D4F54`（无待处理调度中断），又查了一次空 SD 槽，然后在 `0x200D50D4` 调用 `0x2020BFBC`。这条路径把 `0x203E84C0` 的第 3 位用作查表索引。实跑中 EEPROM 偏移 `0x1BBC0 + 1` 的合成 `FF` 让原厂选中空的条目 1；回放在读空指针 `0x20223CA0` 前停下，尚未进入 HOME。更早的原厂 `0x2007B414` 只初始化条目 0 为 `0x203EBCE2`。另一组探针只在 GPIO I²C 初读 `0x1BBC0` 的 32 字节时将第 2 字节改为 `F7`，其余输入不变；原厂取到了自己初始化的条目，走到正常界面调用 `0x200D5114`。这是可复现的**合成设置差异**，未在来宾改指针；不把它称为真机 EEPROM 内容，也尚未证实该位的菜单名称。探针日志：`.analysis/ic705-emulator/agent-cold-radio-a-1115.log`。

### 冷启动后用原厂触屏关闭警告

`0x2004E73C` 通过原厂 GPIO EEPROM 读函数 `0x2005E4C8` 以 32 字节步长载入 `0x202DE844` 描述的五块设置，并各复制一份镜像。滚动比较 `0x2004E820 → 0x20126FC4` 只检查当前 32 字节；发现差异才将不相等的首尾之间送往写入口。三次已拦截的写请求 `0x355C0`、`0x355E6`、`0x3560C` 都在同一个 8,592 字节设置区内。`0x2005C41C` 对总线偏移作位重排：例如 `0x3560C` 实际为 `0x1AB0C`。把原厂在这次合成启动中生成的完整设置区作为只读总线输入（SHA-256 `da46eaad2e52ae166f39fcd68ff45b03880085ccd1d245ffbbea1067280fdbcd`）；它不是任何真机的 EEPROM 备份。两处原厂写入口仍拦截。串口 SCIF2、SCIF4 只模型化实际遇到的寄存器，未提供真机串口数据；见 [Renesas 硬件手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware)第 14 章。

### 冷启动后用机身 MENU 和 EXIT 导航

**通过：同一次从冷启动继续，原厂从关掉警告的 HOME 进入 MENU，再按 EXIT 回到同一个 HOME。** 无键对照保持 HOME；两组均没有持久写入。这个验收还处于合成 `WX-00` 状态，不能把画面当作日版正常收听 CW，也未加载解码扩展。

早期对照的 `0xFCFE0034/44` 位 0 和位 5 是图形处理器与 VDC5 通道 0 的待机请求/应答（[Renesas 硬件手册](https://www.renesas.com/en/document/mah/rza1h-group-rza1m-group-users-manual-hardware) §55.2.22／55.2.24）。模型在实验中确认应答后，原厂确实已关屏蔽 LCD 行中断，不能再送 Vsync。查到 `0x20090664` 经 `0x20090738` 和时长表 `0x20300306` 读取屏保值；合成设置的擦除字节 `FF` 不在合法的 `0–6` 中。按固件的日英设置表 `0x202F085C/98` 与 [Icom 基本手册第 8-17 页](https://www.icomeurope.com/wp-content/uploads/2024/06/IC-705_ENG_IM_Basic_7.pdf) 把电池 / 直流屏保的默认 5 / 60 分钟，即 `03 06`，作为模拟 EEPROM 读取 `0x1CB60` 的 `+14/+15` 两个字节。未改来宾设置内存或放行关屏后的中断。新回放未调用标志清除 `0x200908C0`。REA 镜像取证：`ev_29c8daee273a0931607aa15657f90a370db204a524ee561c135bd15bbfc28e2d`、`ev_cc13abc086ec264a5abbb8cc2d4f80fc2ff4d5c1ca36710ddfc3753f0a3508d3`。

另一个差异是键盘扫描：原厂的前次键值从 `FF` 开始，第一次扫到 MENU 已按下反而被当作基线。先提供松键，等轮扫一轮后再送 MENU，原厂在第 1442 个回放周期解出动作 `5`，进入 `0x200927A4`（页 `02`）和 `0x200927D0`。第 1502 周期，原厂完成 LCD 刷新，图上可辨 MENU 标题和菜单格。EXIT 在第 2336 周期解出动作 `9`；第 2374 周期提交与关闭警告后**逐字节相同**的 HOME RGB565 帧。无键对照全部 27 次扫描无键盘动作，未进入原厂菜单，最后仍是 HOME。原厂页不由脚本写入。
